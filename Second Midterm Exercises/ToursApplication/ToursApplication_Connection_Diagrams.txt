WHY THESE CONNECTIONS EXIST
---------------------------

Web connects to Service:
  Web receives requests and starts the application.
  Service contains actions and scheduled work.

Service connects to Repository:
  Service decides what work should happen.
  Repository knows how to communicate with databases.

Repository connects to databases:
  DbContext performs the actual database queries and changes.

All layers use Domain:
  Domain defines the data being passed between layers.

DIAGRAM 2: PROGRAM.CS DEPENDENCY INJECTION CONNECTIONS
===========================================================

Program.cs teaches the application which concrete class to create when an
interface is requested.


  A class requests:                     Program.cs provides:

  [IRepository<Booking>]  ----------->  [Repository<Booking>]

  [IBookingService]       ----------->  [BookingService]

  [ILegacyTourRepository] ----------->  [LegacyTourRepository]

  [ITourRepository]       ----------->  [TourRepository]


Database registrations:

  [ApplicationDbContext]
           |
           | UseSqlite(DefaultConnection)
           v
       [Local app.db]


  [LegacyTourDbContext]
           |
           | UseSqlServer(LegacyConnection)
           v
       [External ISLegacyDb]


Automatic job registrations:

  AddHostedService<BookCleanUpBackgroundService>()
           |
           v
  Starts booking cleanup automatically


  AddQuartz(...)
       +
  AddQuartzHostedService(...)
           |
           v
  Starts Quartz and schedules QuartzTourEtlJob


WHY DEPENDENCY INJECTION IS USED
--------------------------------

Without dependency injection, every class would need to manually create its
dependencies and know their configuration.

With dependency injection:

  QuartzTourEtlJob asks for ILegacyTourRepository.

  Program.cs knows:

  "When ILegacyTourRepository is requested, create LegacyTourRepository."

The job only knows the interface. Program.cs connects it to the implementation.

DIAGRAM 3: NORMAL HTTP REQUEST AND RESPONSE FLOW
===========================================================

This flow happens when a user sends a request from Postman or a browser.


EXAMPLE: GET ALL TOURS
----------------------

  [Postman]
      |
      | HTTP GET http://localhost:5253/api/Tour
      | Request contains: no body
      v
  [TourController.GetAllAsync]
      |
      | asks for tour responses
      v
  [TourMapper.GetAllAsync]
      |
      | asks for domain Tour objects
      v
  [ITourService]
      |
      | implemented by TourService
      v
  [TourService]
      |
      | asks IRepository<Tour> for local Tours
      v
  [Repository<Tour>]
      |
      | queries ApplicationDbContext
      v
  [ApplicationDbContext]
      |
      | SELECT data
      v
  [Local app.db - Tours table]
      |
      | returns Tour database rows
      v
  [Repository<Tour>]
      |
      | returns List<Tour>
      v
  [TourService]
      |
      | returns List<Tour>
      v
  [TourMapper]
      |
      | converts Tour objects into TourResponse objects
      v
  [TourController]
      |
      | HTTP 200 response with JSON
      v
  [Postman]


REQUEST:

  GET /api/Tour

RESPONSE:

  JSON list of local Tours.

WHY A MAPPER IS USED:

  A domain Tour may contain database/navigation information.
  TourResponse contains only the information intended for API clients.

DIAGRAM 5: BACKGROUNDSERVICE BOOKING CLEANUP FLOW
===========================================================

NO POSTMAN REQUEST IS REQUIRED.


  [Application starts]
          |
          | Program.cs registered AddHostedService
          v
  [BookCleanUpBackgroundService starts automatically]
          |
          | ExecuteAsync begins
          v
  +---------------------------------------------------+
  | while application is still running               |
  |                                                   |
  |  1. Create dependency-injection scope             |
  |                                                   |
  |  2. Get IBookingService                           |
  |                                                   |
  |  3. Ask for cancelled bookings older than 7 days |
  |                                                   |
  |  4. Delete each returned booking                  |
  |                                                   |
  |  5. Wait 3 minutes                                |
  |                                                   |
  |  6. Repeat                                        |
  +---------------------------------------------------+


DETAILED CALL CONNECTION
------------------------

  [BookCleanUpBackgroundService]
          |
          | sends cutoffDate:
          | DateTime.UtcNow.AddDays(-7)
          v
  [IBookingService.GetOldCancelledBookingsAsync(cutoffDate)]
          |
          | interface is implemented by
          v
  [BookingService.GetOldCancelledBookingsAsync]
          |
          | asks repository:
          | Status == Cancelled
          | AND DateCreated < cutoffDate
          v
  [IRepository<Booking>.GetAllAsync]
          |
          | queries local database
          v
  [ApplicationDbContext.Bookings]
          |
          | SQL-like action:
          | SELECT cancelled old bookings
          v
  [Local app.db]
          |
          | returns List<Booking>
          v
  [BookCleanUpBackgroundService]
          |
          | loops through each Booking
          v
  [IBookingService.DeleteByIdAsync(booking.Id)]
          |
          v
  [BookingService.DeleteByIdAsync]
          |
          v
  [Repository<Booking>.DeleteAsync]
          |
          | Remove + SaveChangesAsync
          v
  [Local app.db - Bookings table]
          |
          | booking is deleted
          v
  [BookCleanUpBackgroundService]
          |
          | waits 3 minutes
          v
  [Next cleanup execution]


INPUT TO THE BACKGROUND JOB:

  No HTTP request.
  The current time and local Bookings data.

OUTPUT FROM THE BACKGROUND JOB:

  Matching bookings are deleted.
  Information and errors are written to console logs.


WHY THE JOB USES IBOOKINGSERVICE:

  The background job controls when cleanup happens.
  BookingService controls how booking operations happen.

This keeps responsibilities separate.

DIAGRAM 7: QUARTZ ETL COMPLETE FLOW
===========================================================

NO POSTMAN REQUEST IS REQUIRED.


  [Application starts]
          |
          | Program.cs starts QuartzHostedService
          v
  [Quartz Scheduler starts]
          |
          | Cron trigger every 5 minutes:
          | 0 0/5 * * * ?
          v
  [QuartzTourEtlJob.Execute]
          |
          | EXTRACT + TRANSFORM TOURS
          v
  [ILegacyTourRepository.GetTourAsync]
          |
          v
  [LegacyTourRepository.GetTourAsync]
          |
          | reads through LegacyTourDbContext
          v
  [External SQL Server - ToursDirectory]
          |
          | returns Name + Capacity
          v
  [LegacyTourRepository]
          |
          | transforms each row into Tour:
          | Name -> Tour.Name
          | Capacity -> Tour.Capacity
          | Name -> deterministic Tour.Id
          v
  [List<Tour>]
          |
          | LOAD TOURS
          v
  [ITourRepository.BulkInsertOrUpdateToursAsync]
          |
          v
  [TourRepository]
          |
          | uses ApplicationDbContext
          v
  [Local app.db - Tours table]
          |
          | insert new Tours or update existing Tours
          v
  [QuartzTourEtlJob]
          |
          | EXTRACT + TRANSFORM OFFERS
          v
  [ILegacyTourRepository.GetOffersAsync]
          |
          v
  [LegacyTourRepository.GetOffersAsync]
          |
          | reads through LegacyTourDbContext
          v
  [External SQL Server - TourOfferings]
          |
          | returns AgencyName + TourName
          v
  [LegacyTourRepository]
          |
          | also reads local TravelAgencies
          v
  [ApplicationDbContext - TravelAgencies]
          |
          | returns AgencyName -> TravelAgencyId mapping
          v
  [LegacyTourRepository]
          |
          | transforms each row into Offers:
          | TourName -> Offers.TourId
          | AgencyName -> Offers.TravelAgencyId
          | AgencyName + TourName -> Offers.Id
          v
  [List<Offers>]
          |
          | LOAD OFFERS
          v
  [ITourRepository.BulkInsertOrUpdateOffersAsync]
          |
          v
  [TourRepository]
          |
          | uses ApplicationDbContext
          v
  [Local app.db - Offers table]
          |
          | insert new Offers or update existing Offers
          v
  [QuartzTourEtlJob logs result and finishes]
          |
          | Quartz waits for next trigger
          v
  [Next execution after 5 minutes]


INPUT TO THE QUARTZ JOB:

  No HTTP request.
  External ToursDirectory records.
  External TourOfferings records.
  Existing local TravelAgency records.

OUTPUT FROM THE QUARTZ JOB:

  Local Tours are inserted or updated.
  Local Offers are inserted or updated.
  Execution result is written to console logs.

DIAGRAM 8: ETL - EXTRACT, TRANSFORM, LOAD
===========================================================

                         ETL

  EXTRACT                  TRANSFORM                 LOAD
  -------                  ---------                 ----

  External DB              LegacyTourRepository      Local DB

  ToursDirectory     --->  LegacyToursDirectory ---> Tour
  Name                     Name -> Name              Tours table
  Capacity                 Capacity -> Capacity
                           Name -> Guid Id


  TourOfferings      --->  LegacyTourOfferings  ---> Offers
  AgencyName               AgencyName -> AgencyId    Offers table
  TourName                 TourName -> TourId
                           both names -> Offer Id


WHY TRANSFORMATION IS REQUIRED:

The external database identifies records using names.
The local database identifies records using Guid IDs.

LegacyTourRepository converts the external names into the IDs expected by the
local entities.

DIAGRAM 9: GUIDHELPER AND DUPLICATE PREVENTION
===========================================================

BAD APPROACH WITH Guid.NewGuid()
-------------------------------

First ETL:

  "Summer Tour" ---> random Guid A ---> inserted

Second ETL:

  "Summer Tour" ---> random Guid B ---> inserted again

Result:

  Duplicate Tours.


CURRENT APPROACH WITH GuidHelper
--------------------------------

First ETL:

  "Tour" + "Summer Tour"
          |
          v
      GuidHelper
          |
          v
       Guid A
          |
          v
       inserted


Second ETL:

  "Tour" + "Summer Tour"
          |
          v
      GuidHelper
          |
          v
       same Guid A
          |
          v
       existing record updated


WHY ENTITY TYPE IS INCLUDED:

  GuidHelper.FromLegacyId("Tour", key)
  GuidHelper.FromLegacyId("Offer", key)

Including the entity type separates Tour IDs from Offer IDs.

DIAGRAM 10: EXTERNAL OFFER TO LOCAL OFFER MAPPING
===========================================================

External TourOfferings row:

  AgencyName = "Sunny Escapes"
  TourName   = "Summer Tour"


TOUR ID MAPPING
---------------

  TourName = "Summer Tour"
          |
          v
  GuidHelper.FromLegacyId("Tour", "Summer Tour")
          |
          v
  Offers.TourId


AGENCY ID MAPPING
-----------------

  AgencyName = "Sunny Escapes"
          |
          v
  Look inside local TravelAgencies
          |
          v
  Find TravelAgency where Name == "Sunny Escapes"
          |
          v
  Use existing TravelAgency.Id
          |
          v
  Offers.TravelAgencyId


OFFER ID MAPPING
----------------

  "Sunny Escapes" + ":" + "Summer Tour"
          |
          v
  GuidHelper.FromLegacyId("Offer", combined names)
          |
          v
  Offers.Id


Final local Offers object:

  Offers
  {
      Id             = deterministic Offer Guid
      TourId         = deterministic Summer Tour Guid
      TravelAgencyId = existing Sunny Escapes Guid
  }

DIAGRAM 11: WHY TOURS MUST BE SAVED BEFORE OFFERS
===========================================================

  [Tour]
    Id = TourId
        ^
        |
        | foreign-key relationship
        |
  [Offers]
    TourId = TourId


Correct order:

  1. Save Tours
  2. Save Offers


Incorrect order:

  1. Save Offers
  2. Tour does not exist yet
  3. Foreign-key error may happen


That is why QuartzTourEtlJob performs:

  Get Tours
      ->
  Save Tours
      ->
  Get Offers
      ->
  Save Offers

===========================================================
PRESENTATION VERSION
===========================================================

"The application has three different flows.

The first is the normal API request flow. Postman sends a request to a
controller. The controller uses a mapper and service. The service uses a
repository, and the repository reads or changes the local database. The result
then returns to Postman as an HTTP response.

The second is the booking cleanup flow. It does not need Postman. Program.cs
starts BookCleanUpBackgroundService automatically. Every three minutes it asks
BookingService for cancelled bookings older than seven days. BookingService
uses Repository<Booking> and ApplicationDbContext to delete them from app.db.

The third is the ETL flow. It also does not need Postman. Program.cs starts
Quartz, and Quartz triggers QuartzTourEtlJob every five minutes. The job uses
LegacyTourRepository and LegacyTourDbContext to read ToursDirectory and
TourOfferings from the external SQL Server. The repository transforms them
into local Tour and Offers objects. TourRepository then uses
ApplicationDbContext to insert or update them in local app.db."
